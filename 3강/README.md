# 그르르AI — 나만의 AI 에이전트 만들기 · 3강

이 폴더는 그르르AI 채널 실습편 3강용 자료입니다.
1·2강에서 만든 에이전트(정체성 + 텔레그램 연결 + 스케줄러)에 이어서, **문의 한 건이
들어와서 처리 완료되기까지의 여정**을 자동화 수준을 높여가며 완성해봅니다.

⚠️ **아직 촬영 전이라 실제 코드는 없습니다.** 1·2강과 달리 이번 강의는 완성된 스크립트를
복사해서 쓰는 대신, **촬영 중에 에이전트에게 직접 프롬프트로 만들어달라고 하는 과정 자체가
콘텐츠**입니다 — "나만의 에이전트" 시리즈 취지상, 사전에 만들어둔 코드를 재생하는 게 아니라
실제 사용자가 에이전트에게 말을 걸어가며 눈앞에서 자동화를 함께 완성해가는 걸 보여주기
위해서입니다. 아래 내용은 브레인스토밍으로 미리 정한 설계와 겪었던 함정들을 미리 공유하는
것이고, 실제 코드와 최종 README는 촬영·편집이 끝나는 대로 이 폴더에 채워집니다.

## 이번 강의에서 다루는 것

- **핵심 도구**: 구글폼/스프레드시트(문의 입력구) → 노션(저장·이력·팀 업무현황) →
  슬랙(부서 전달) → 텔레그램(컨펌 UI, 1·2강에서 만든 그 에이전트를 그대로 씁니다)
- **차별점**: "노션 하나만 쓰는 자동화"가 아니라, 여러 모듈(시트·노션·슬랙·텔레그램)을
  넘나드는 라우팅을 보여주는 것이 핵심입니다.
- **단계 구조**: 1단계(완전 수동 컨펌) → 2단계(AI 판단 + 사람 확인)로 자율성이 올라가는
  하나의 이야기입니다. 3단계(리스크 기반 자동실행)는 이번 강의 범위 밖이고, 마지막에
  한 줄 티저만 남깁니다.

## 인증 설정 — 미리 알아두면 좋은 함정들

### 구글 (Sheets 자동화용)

1. console.cloud.google.com에서 새 프로젝트 생성
2. API 및 서비스 > 라이브러리에서 **Google Sheets API** 사용설정
3. ⚠️ **Google Drive API도 반드시 같이 사용설정해야 합니다.** Sheets API만 켜면 기존
   시트 읽기/쓰기는 되지만, **새 시트를 생성하려고 하면 403 에러**(`Google Drive API
   has not been used in project...`)가 납니다.
4. IAM 및 관리자 > 서비스 계정 > 서비스 계정 만들기 → 키 탭에서 JSON 키 발급
5. 시트를 만든 뒤, JSON 안의 `client_email`에게 편집자 권한으로 공유
   - ⚠️ 서비스계정 자체는 구글 드라이브 저장공간이 0이라 **새 파일을 직접 만들 수
     없습니다.** 그래서 시트/폼은 사람이 UI에서 직접 만들고, 그 파일을 서비스계정
     이메일에 공유해주는 방식으로 진행합니다 — 아래 노션의 "페이지 하나는 사람이
     직접 만들어야 한다"는 제약과 똑같은 패턴입니다.
6. 구글폼 만들기: 시트에서 **"도구 > 설문지 만들기"**, 질문 2개(이메일, 문의사항)만
   추가합니다. **부서 질문은 의도적으로 넣지 않습니다** — 부서는 1단계에서 채팅으로
   정해지는 값이라 입력 단계에는 포함하지 않는 게 맞습니다(아래 1단계 참고).

### 노션

노션은 **콘텐츠(페이지+DB, 위 샘플 링크)는 그대로 쓰고, 통합(앱 연결) 등록만 처음부터
직접 해봅니다** — "노션에 앱을 어떻게 연결하는지" 그 등록 과정 자체를 보여주는 게 목적입니다.

1. notion.so/my-integrations → **"+ 신규 연결"** 클릭
   - 연결 이름 입력, 범위(단일 워크스페이스 / 다중 워크스페이스) 선택
   - **인증 방법**에서 **액세스 토큰** 선택(OAuth 아님 — 이런 자동화 스크립트엔 단순 토큰 방식이 맞습니다)
   - **설치 가능 워크스페이스**에서 워크스페이스 선택 → 생성
   - 생성 완료 화면에서 토큰(`ntn_`로 시작)이 표시됩니다 → 복사
   - 노션 가입 시 개인 워크스페이스가 자동으로 하나 생기므로, 워크스페이스를 따로 미리 만들어둘 필요는 없습니다
2. ⚠️ **내부 통합은 API로 워크스페이스 최상단에 새 페이지를 만들 수 없습니다**
   (`insert_content` 권한 정책). 그래서 위 샘플 페이지처럼 사람이 빈 페이지 하나를
   직접(또는 복제로) 먼저 만들고, 그 페이지 "..." 메뉴 > Connections에서 방금 만든
   통합을 연결해줘야, 그 페이지 아래부터 API로 자동 생성/조회가 가능해집니다.
3. 위 샘플을 복제했다면 이미 DB 4개(팀원 업무현황·과거 처리 이력·접수된 문의·팀 업무
   배정 목록)가 갖춰져 있습니다 — 처음부터 만드는 경우엔 최소 **"팀원 업무현황"**
   (팀원별 진행업무·여유도), **"과거 처리 이력"**(부서별 과거 처리 건, 2단계에서 AI가
   검색할 소스) 2개만 있어도 충분합니다.

### 슬랙

1. 새 워크스페이스 생성 → api.slack.com/apps에서 **Create New App**
2. ⚠️ **UI가 바뀌었습니다** — 예전에 "From scratch"였던 옵션이 지금은 **"Blank app"**
   으로 이름이 바뀌어 있습니다.
3. OAuth & Permissions에서 Bot Token Scopes에 `reactions:read`, `chat:write`,
   `channels:manage` 추가 후 Install to Workspace
4. ⚠️ **채널 생성 스코프 이름 관련 시행착오**: `channels:write`를 찾으면 UI에 그
   이름이 안 보이고 `channels:write.invites`/`channels:write.topic`처럼 더
   세분화된 이름만 보입니다 — 실제로 필요한 건 **`channels:manage`**입니다.
5. ⚠️ **아키텍처 변경 이력**: 처음엔 Incoming Webhook 방식으로 시작했는데, 만들어보니
   **웹훅 하나는 특정 채널 딱 하나에만 고정 전송되는 구조**라는 걸 알게 됐습니다 —
   이 파이프라인은 "5개 부서 채널 중 골라서 전송"해야 하는데 웹훅으로는 안 됐습니다.
   그래서 **봇토큰의 `chat.postMessage` API로 전환**했습니다 — 봇 하나(`chat:write`
   +`reactions:read`+`channels:manage`)로 메시지 전송, 완료감지 폴링, 채널 생성을
   전부 처리합니다.
6. 부서 채널 5개(고객지원/기술지원/결제정산/영업/운영)를 봇 토큰으로
   `conversations.create` 호출해서 만들고, 각각 실제 업무처럼 보이는 이전 대화 몇
   개씩 시드합니다.
7. ⚠️ **슬랙은 노션/구글시트처럼 "복제해서 가져가기"가 안 됩니다** — 워크스페이스·앱
   자체는 Duplicate 개념이 없습니다. 시청자에게는 "이 워크스페이스를 복제해가는 게
   아니라, 본인 워크스페이스에 채널을 직접 만들고 봇을 초대하면 된다"고 안내할
   예정입니다. 슬랙 봇 앱 등록(스코프 설정·설치)은 진입장벽이 있는 부분이라, 메신저는
   "슬랙 자리에 원하는 도구로 갈아끼우면 된다"는 프레이밍을 유지하고, 대안으로
   텔레그램 봇(1·2강에서 이미 써본 방식, 진입장벽이 제일 낮음)도 언급합니다.

### 텔레그램 — 인라인 버튼을 폐기하고 "채팅으로 말하기"로 확정한 이야기

**⚠️ 처음 시도했던 방식(인라인 키보드 버튼 + 콜백 캡처)은 실제로 리허설해보니
구조적으로 불안정해서 폐기했습니다.** 이 실패 과정 자체가 재밌는 소재라 그대로
공유합니다.

**시도 1 — 인라인 버튼 + `getUpdates` 폴링 (폐기)**
"부서 선택" 같은 인라인 키보드 버튼과 콜백 수신은 Claude Code의 텔레그램 플러그인
reply 도구로는 처리할 수 없습니다(버튼/콜백 미지원) — 그래서 텔레그램 Bot API를
파이썬에서 직접 호출하는 별도 스크립트로 버튼을 보내고, `getUpdates` 폴링으로
`callback_query.data`를 캡처하는 방식을 실제로 만들어서 테스트했습니다.

**실제로 겪은 문제**: 대화 중인 세션(텔레그램 플러그인)도 같은 봇 토큰으로
`getUpdates`를 상시 폴링하고 있어서, 별도 폴링 스크립트가 같은 토큰으로
`getUpdates`를 호출하면 **`409 Conflict: terminated by other getUpdates request`**가
뜹니다. 텔레그램 Bot API는 토큰 하나당 폴러를 딱 1개만 허용하는 공식 정책이라(주요
봇 라이브러리들의 이슈트래커에서 전세계적으로 똑같이 보고되는 제약, 우회법 없음),
실제로 6번 연속 재시도해도 한 번도 못 잡히는 경우까지 확인했습니다.

**시도 2 — 채팅으로 부서명 말하기 (✅ 최종 채택)**
새 문의가 오면 사용자가 문의 내용을 보고 **"이건 결제정산이네"처럼 그냥 채팅으로
부서명을 말합니다.** 에이전트가 그 말을 듣고 스크립트를 실행해서 노션 업데이트 +
슬랙 전송을 처리합니다. 버튼도, 콜백 캡처도, 폴링 경쟁도 필요 없습니다 — 이미
안정적으로 작동하는 일반 텔레그램 메시지 경로를 그대로 쓰기 때문에 구조적으로 실패할
일이 없습니다.

오히려 이 시리즈("나만의 에이전트")의 정체성에 더 잘 맞습니다 — "버튼을 설계해서
자동화를 흉내내는" 게 아니라 "사람이 자연어로 말하고 에이전트가 알아서 실행하는"
게 이 시리즈가 계속 보여주고 있는 패턴입니다. 부서 판단은 여전히 100% 사람 몫이고
(1단계는 고정메뉴/사람판단이라는 원칙 그대로), 달라진 건 "어떤 인터페이스로 그 판단을
전달하느냐"뿐입니다.

## 1단계 — 완전수동 컨펌 파이프라인

부서 분류는 AI 판단이 아니라 고정 메뉴 선택이라, 이 단계는 끝까지 100% 사람 확인으로
진행됩니다.

1. **구글폼으로 문의 입력** — 문의를 제출하면 구글시트의 "설문지 응답 시트1" 탭에
   타임스탬프/이메일/문의사항 3컬럼으로 자동 적재됩니다.
2. **파이썬 자동화가 새 행 감지 → 노션에 저장**
   - ⚠️ **함정 1**: 폼 응답이 항상 맨 아래에 추가되는 게 아닙니다 — 실제로 새로
     제출한 응답이 헤더 바로 다음 행(2행)에 꽂히면서 기존 데이터가 전부 아래로 밀린
     사례가 있었습니다. "마지막 행만 확인"하는 방식으로 새 행을 감지하면 이런 경우
     새 문의를 놓칩니다 — 매번 전체 행을 읽어서 "이미 처리한 행 집합"과 비교하는
     diff 방식으로 감지해야 합니다.
   - ⚠️ **함정 2**: 노션 날짜 속성에 오프셋 없는 로컬 시각 문자열을 그대로 넣으면
     노션이 이걸 UTC로 조용히 해석해버려서 실제로는 9시간 밀린 시각이 저장됩니다.
     날짜를 쓸 때는 항상 `+09:00`처럼 명시적 타임존 오프셋을 붙여야 합니다.
3. **에이전트가 텔레그램으로 신규 문의 내용을 알림**
4. **채팅으로 부서명을 말하면 기록 + 해당 부서 슬랙 채널로 자동 전송** — 부서 판단은
   100% 사람 몫이고, 에이전트는 그 말을 받아 기계적으로 실행만 합니다.
5. **담당자가 처리 완료하면 그 슬랙 메시지에 ✅ 이모지 리액션**
6. **주기적으로 슬랙 폴링으로 완료 감지** (`reactions.get`)
7. **감지되면 노션 상태를 "완료"로 업데이트 + 텔레그램 알림**

**완료감지 방식을 폴링으로 택한 이유**: 처음엔 Interactive Button(앱등록+OAuth+공개
웹훅서버 필요, 진입장벽 높음)을 고려했다가, Workflow Builder(이모지 트리거+웹훅 액션,
앱등록은 불필요하지만 **슬랙 무료 플랜에서는 안 되고 Pro 플랜부터 가능**)로 넘어갔다가,
최종적으로 **폴링 방식**(`reactions.get`, 읽기 스코프 봇토큰만 있으면 됨, 공개서버
불필요, 무료플랜에서도 동작)으로 확정했습니다.

## 2단계 — AI 판단 + 사람 확인

1단계에서 슬랙으로 부서에 전달된 문의가, 이제 그 부서 입장에서는 "실제로 처리해야 할
업무"가 됩니다. 문의(공통)와 업무(부서 내부 추적)는 노션에서 별도 DB로 분리합니다 —
공통 문의사항 인박스와 팀 내부 업무 추적은 성격이 다른 데이터이기 때문입니다.

1. "접수된 문의" DB에서 이 문의를 조회 (1단계의 연장선, 새로 저장하지 않음)
2. `claude -p` 헤드리스 에이전트가 조회: 노션 DB "팀원 업무현황"에서 팀원별 현재
   업무현황(여유도), 노션 DB "과거 처리 이력"에서 유사한 과거 업무 처리 이력
3. 이 둘을 종합해서 **담당자 / 우선순위 / 마감기한** 3개 값을 판단
4. 판단 결과와 근거(참고한 과거 유사사례)를 텔레그램으로 보여주고 컨펌
5. 컨펌되면 "팀 업무 배정 목록" DB에 새 페이지로 확정 저장

핵심은 "부서 분류"(1단계, 고정메뉴)와 "담당자/우선순위/마감기한 판단"(2단계, AI+근거
제시)의 차이입니다 — 누가 판단하느냐가 사람에서 AI로 바뀌지만, 최종 확정은 여전히
사람의 컨펌을 거칩니다.

## 3단계 티저

3단계는 이번 강의 범위에 포함하지 않고, 영상 마지막에 한 줄 티저만 남깁니다.

> "다음 단계는, 리스크에 따라 AI가 스스로 실행 여부까지 판단하는 것입니다."

## 아키텍처 원칙

MCP는 에이전트가 진짜 판단해야 하는 순간에만 쓰고, 정해진 로직대로 반복되는
자동화(폴링, 저장 등)는 각 서비스의 REST API를 파이썬으로 직접 호출합니다. 노션은
REST API가 있으니 반복적이고 정형화된 작업(검색·기록)은 스크립트가 직접 처리하고,
에이전트(AI)는 진짜 판단이 필요한 부분(부서/담당자 판단, 문구 작성, 우선순위 결정)에만
개입합니다.

## 실습 vs 시연

- **직접 따라할 수 있는 부분**: 구글시트/폼 macro, 노션 템플릿복제+API통합 — 진입장벽이
  낮아서 시청자 본인 계정으로 그대로 실습 가능합니다.
- **"보기" 위주인 부분**: 슬랙 봇 앱 등록은 앱 등록이 필요해 진입장벽이 있습니다.
  실제 시연은 실제 슬랙 워크스페이스로 라이브 진행합니다.
